# Architecture — internal generation

## Human authorization invariant

KajovoCML has exactly one human authorization role: `OWNER`. The active
authorization path does not distinguish `ADMIN`, `AUDITOR` or another human
role. Forward-only migration `025_single_owner_human_role.sql` normalizes
legacy account rows and enforces `admin_account.role = 'OWNER'` without
changing account identity, session/MFA/recovery data or audit attribution.
The API and admin UI do not accept or offer role selection; active status,
MFA, sessions, reauthentication, CSRF and last-owner safety remain separate
controls. Machine/service principals and their permissions are not human roles
and retain their canonical principal-kind/grant model.

OWNER submits free text to `/api/generation/jobs`. The persistent generation worker leases the job, produces/accepts a plan, reserves final component identities, creates a local revision point/workspace, runs the focused OpenAI Responses orchestration, validates generated handlers/manifests, installs a versioned local release and starts the real UDS runtime.

The result is registered directly into the existing canonical `component`/`principal` model. Secret Manager grants bind directly to that identity. Planner dependencies materialize as the existing component/principal permissions and are verified by real cross-component calls through the canonical HTTPS `/mcp` boundary. Existing control queue, state/heartbeat, monitoring, readiness/E2E evidence and audit remain the only control plane.

External MCP callers are authorized at the CML HTTPS boundary. For `INTERNAL_GENERATED` targets CML then resolves that target's single managed runtime credential from the existing Secret Manager and dispatches JSON-RPC to the local UDS `/mcp`; the external bearer is never forwarded as the generated runtime credential. Generated provider webhooks are public CML-owned `/webhooks/...` endpoints with provider-specific challenge/HMAC verification and the same internal credential handoff to the generated endpoint handler.

Generated `handler.mjs` business logic never runs as a normal trusted Node module. `runtime-host.mjs` launches it in an unprivileged user+mount+network namespace with a minimal read-only chroot, then evaluates it through the restricted module/context loader. The generated process has no host network namespace, no host filesystem view, no runtime credential environment, no direct Node module loader, `process`, `fetch` or runtime string-code generation in the handler context. The trusted runtime host exposes only JSON capability calls for existing CML mechanisms: `context.secret`, `context.callComponent`, `context.callExternal` and bounded persistent `context.state`. The runtime host remains the only process with the Node/network/filesystem authority needed to implement those CML capabilities.

Generation owns one job-scoped Playwright session record and retains its isolated Playwright BrowserContext for the active session, including popup/login continuity. Migration `026_generation_browser_session_contract.sql` persists the session lifecycle, monotonic preview-frame metadata, external-operation scopes, irreversible confirmations and teaching evidence; preview bytes use a job namespace and are deleted on cancellation. `playwright-session.mjs` starts Playwright-managed Chromium without `--no-sandbox`, applies HTTPS/private-network guards, isolates the context and exposes only semantic locator actions. Preview is event-driven and returns only a normal PNG frame or an explicit sensitive/no-preview status; it never returns a filesystem path. Secret Manager-backed field entry remains part of the same browser session; browser credentials are bound to the existing platform principal and no second credential/control plane is created.

The canonical `browser-automation-runtime.mjs` interprets an immutable declarative manifest (`NAVIGATE`, `CLICK`, `FILL`, `FILL_SECRET`, `SELECT`, `CHECK`, `UNCHECK`, `PRESS`, `UPLOAD`, `DOWNLOAD`, `WAIT_FOR`, `ASSERT`, `EXTRACT`, `BRANCH`, and bounded `REPEAT_BOUNDED`) through the same Playwright platform boundary. It accepts semantic locators and explicit observed-state predicates only; it has no arbitrary JavaScript, `page.evaluate`, shell, direct fetch, or generated runtime source path. The DB-backed `domain/browser-automation.ts` and `kcml-browser-automation-worker.service` persist definitions, immutable revisions, fenced leases, idempotent runs, step checkpoints, cancellation and protected evidence without calling OpenAI. The worker records a fresh `BROWSER_AUTOMATION` heartbeat in the existing platform-worker heartbeat table, and readiness requires that heartbeat together with generation and canonical component worker heartbeats. Static preflight remains distinct from runtime verification: the owner-facing runtime verification route executes the same interpreter only for explicitly `READ_ONLY` manifests, and only that measured result can produce `verification_status=PASS` for activation. Auth binding creation is metadata-only and runtime resolution goes through the existing Secret Manager/platform principal boundary. An OWNER repair request now records an audit event and enqueues the existing inherited-spec generation repair authority for the owning component; missing ownership or approved functional lineage fails closed as a blocked repair. Uncertain side effects are finalized as `MANUAL_REVIEW`, never as a blind retry. Full human challenge, drift reconciliation and component-release activation ordering remain separate acceptance items. Generated handlers cannot import or access this runtime directly; they must call the canonical CML component boundary.

Generation discussion persistence is defined by migrations `014_generation_discussion.sql` and `015_browser_automation_runtime.sql`, with forward completion through `026_generation_browser_session_contract.sql`. Messages, turns, spec revisions and event sequences are durable, approval freezes revision+digest, and `/api/generation/jobs/:id/events` provides replayable SSE. Discussion leases carry a fencing token; every streaming delta, tool event, spec write and terminal update is guarded by the current token, so a worker that loses its lease cannot publish late output. The OWNER API exposes authenticated, CSRF-protected job-scoped preview, credential binding, operation-scope, irreversible-confirmation and teaching/preflight/replay routes; deterministic candidate replay calls the same manifest interpreter as production and makes zero model calls.

Before a new capability is proposed, the discussion worker performs canonical capability-first discovery through the existing component, active revision, tool contract, readiness and principal data. It records only safe per-turn evidence. New specification decisions are machine-readable `FULL_REUSE`, `PARTIAL_REUSE` or `NEW_CAPABILITY_REQUIRED`; exact component/revision/tool digests are revalidated immediately before approval. A historical specification without this optional field remains valid without rewriting its canonical JSON or digest.

Specification proposal failures are recoverable inside the same bounded Responses chain. The server returns only safe schema-path/error-class diagnostics and refuses to complete the discussion turn with ordinary text while a proposal failure remains unresolved. A valid `propose_generation_specification` call must clear that condition; otherwise the turn ends as a bounded failure without creating a revision.

OWNER cancellation is authoritative. A worker polls the persisted job state, propagates cancellation through model HTTP, shell commands and the browser session, checks the authoritative state at phase/deploy/activation boundaries and uses guarded state updates that cannot overwrite `CANCELLED`. Candidate local releases are rolled back/removed on cancellation while a pre-existing functional release is preserved.

The same canonical candidate cleanup is used when a post-deploy technical failure abandons a revision. A first CREATE with no `previous_release_id` stops the generated runtime, removes its `current` link and marks that local release `ROLLED_BACK` before a remediation revision may start. UPDATE/REPAIR rolls back to the previous local release. Whenever a REPAIR candidate is abandoned, the captured repair-base lifecycle/control state is restored after the release rollback, including terminal failure after remediation exhaustion. Ordinary INTEGRATING retry keeps the current live candidate because that revision has not yet been abandoned.

The implementation Responses loop cannot terminate successfully with stale or invalid artifacts. The server re-reads each final manifest/handler pair, validates it against the workspace copy of the canonical component schema and runs Node syntax checking. Safe validation errors are fed back into the same bounded provider conversation for correction; only a final all-valid set can enter registration and candidate deployment.

If INTEGRATING is `BLOCKED` with `OWNER_INPUT_REQUIRED` for a runtime secret, OWNER submission uses the existing Secret Manager upsert/rotate path and commits deterministic PLATFORM/COMPONENT grants before the persisted job state is returned to `INTEGRATING`. If the requested ACTIVE secret already exists, the same component grants are reconciled before continuing without an OWNER prompt. Therefore the first provider callback after resume can resolve the candidate's required secret.

Activation is fail-closed until local runtime validation and actually measured CML conformance pass. Undeclared capabilities are `NOT_APPLICABLE`, not synthetic PASS. Completion verifies canonical HTTPS `tools/call`, control/state/heartbeat, monitoring/watchdog, Secret grants, declared endpoints/pulses/dependencies/external access and audit as applicable. Failure disables the candidate and rolls back to the previous local release when available; first-release candidates are explicitly stopped/removed rather than left ACTIVE without a rollback target.

The production monitoring/watchdog uses the same runtime probe implementation as conformance. A measured runtime/contract fault on an active `INTERNAL_GENERATED` component may enqueue a deduplicated/cooldown `REPAIR` generation job against its active local release. Repair uses the captured monitoring evidence, preserves component identity, reruns the normal generation/deploy/conformance path, restores the last functional release on failure, and inherits the exact approved specification digest from the functional lineage with `INHERITED_TECHNICAL` authority. Technical retry/remediation keeps that same frozen authority and never uses `original_prompt` or diagnostic prose as a replacement specification. Without that lineage it is created `BLOCKED` with `generation_repair_spec_lineage_missing`, never `IMPLEMENTING`, so an OWNER follow-up must create a new discussion and approval. If enqueue itself fails, the scheduler continues but records a component-scoped `component.repair.enqueue_failed.<componentId>` operational alert and `generated_component.repair_enqueue_failed` audit event with correlation ID and technical reason; a later normal cycle can retry and close the alert when recovered.

The generated-component systemd template loads the runtime token as a systemd credential; runtime code/release files are read-only and writable state is restricted to runtime/data paths. Rotation updates the managed secret + systemd credential and restarts the instance; revocation disables the credential and stops the instance.
